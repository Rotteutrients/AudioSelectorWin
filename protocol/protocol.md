# Audio Selector バイナリプロトコル仕様 バージョン1

## 1. 文書の位置づけと適用範囲

本書は、Audio Selectorのバイナリプロトコルバージョン1の正式仕様である。本文中の要求レベルは以下の意味で使用する。

- **必須（MUST）**: 必ず実装・遵守する
- **禁止（MUST NOT）**: 実装・実行してはならない
- **推奨（SHOULD）**: 特別な理由がない限り実装・遵守する
- **非推奨（SHOULD NOT）**: 特別な理由がない限り実装・実行しない
- **任意（MAY）**: 実装を選択できる

本プロトコルは、Windows上のRustアプリケーション（**ホスト**）とESP32 Audio Selector（**デバイス**）間で、Windowsのオーディオエンドポイントの状態とユーザー操作要求を伝送する。

バージョン1は通常Bluetooth Classic SPP上で動作する。ただし、本プロトコル自体はSPPに依存せず、通信路を順序保証された信頼性のあるバイトストリームとして扱う。1回の読み取りまたは書き込みが1メッセージの境界と一致することを前提としてはならない。

Windowsを常に正しい情報源とする。デバイスはエンドポイント変更要求の成功を推測してはならない。

## 2. バイト列の共通規則と上限値

| 項目 | バージョン1の値 |
| --- | ---: |
| 複数バイト整数のバイト順 | リトルエンディアン |
| 真偽値のfalse / true | `0x00` / `0x01` |
| 文字列符号化 | NUL終端なしのUTF-8 |
| 最大ペイロード長 | 512バイト |
| エンドポイント表示名の最大符号化長 | 240バイト |
| エラー詳細文字列の最大長 | 240バイト |
| データフローごとの最大エンドポイント数 | 64 |
| エンドポイントハンドル幅 | 16ビット |
| 無効または不在を表すエンドポイントハンドル | `0x0000` |

`u16`などはそのビット幅の符号なし整数を意味する。予約フィールドおよび予約フラグビットは送信時に必ず0とし、受信側はその値を無視する。

特記がない文字列は次の形式とする。

```text
+----------------+----------------------+
| byte_length    | UTF-8 バイト          |
+----------------+----------------------+
| u16            | byte_length バイト    |
+----------------+----------------------+
```

長さはUnicode文字数や表示桁数ではなくバイト数を示す。文字列を短縮する場合は正しいUTF-8の文字境界で切らなければならない。受信側は不正なUTF-8を拒否する。エンドポイント名がUTF-8で240バイトを超える場合、送信用の表示名を短縮する。この短縮は完全なWindowsエンドポイントIDやホスト内部の表示名を変更しない。

## 3. フレーム形式

すべてのフレームは6バイトのヘッダーと、その直後のペイロードで構成する。埋め草、終端文字、エスケープ処理、チェックサムは使用しない。

```text
offset  size  field
0       2     magic: 0x41 0x53（ASCII "AS"）
2       1     protocol_version: 0x01
3       1     message_type
4       2     payload_length: u16, リトルエンディアン
6       N     payload
```

`payload_length`は0以上512以下で、各メッセージ仕様が要求するペイロード長と完全に一致しなければならない。受信側は余分なバイトや不足したバイトを有効なメッセージの一部として解釈してはならない。

SPP/RFCOMMがリンク層の整合性検査と再送を提供するため、バージョン1ではアプリケーション層のCRCを使用しない。互換性のないフレーム形式の変更には、新しいプロトコルバージョンを割り当てる。

### 3.1 ストリーム解析と復旧

受信側は永続的な受信バッファを保持し、未完フレームおよび1回の読み取りに複数フレームが含まれる場合に対応しなければならない。解析手順は次のとおりとする。

1. `0x41 0x53`を検索し、それより前のバイトを破棄する。バッファ末尾の単独の`0x41`は、次回読み取りでマジック値の先頭になる可能性があるため保持する。
2. 6バイトのヘッダーが揃うまで待機する。
3. `payload_length`を読み取る。512を超える場合は先頭のマジック値の先頭バイト `0x41`だけを破棄し、マジック値の検索を再開する。宣言されたペイロードの到着を待ってはならない。
4. `6 + payload_length` バイトが揃うまで待機する。
5. 状態へ反映する前に、バージョン、種別、ペイロードの正確な構造、列挙値、予約フィールド、UTF-8を検証する。
6. 完全なフレームを正確に消費する。未知のメッセージ種別でも長さが有効なら、宣言された長さ分を消費して`ERROR(UNKNOWN_TYPE)`を返す。

状態を変更するメッセージを部分的に反映してはならない。受信バッファ全体は2048バイト以下に制限することを推奨する。有効なフレームを抽出できないまま上限を超える場合、バッファを消去し、可能なら`ERROR(RECEIVE_BUFFER_OVERFLOW)`を通知して再接続することを推奨する。

## 5. 接続とハンドシェイク

SPPストリーム確立後、両通信相手は以前の接続に属する状態を破棄する。ホストは2秒以内に`HELLO_REQ`を送信しなければならない。ハンドシェイク成功前に受け付けるメッセージは、方向が適切な`HELLO_REQ`、`HELLO_RESP`、`PING`、`PONG`、`ERROR`だけとする。

### 5.1 `HELLO_REQ` (`0x01`)

```text
offset  field                 type   必須値 / 意味
0       minimum_version       u8     0x01
1       maximum_version       u8     0x01
2       host_capabilities     u32    機能ビットマップ
6       host_nonce            u32    接続ごとの乱数値
10      reserved              u16    0
```

### 5.2 `HELLO_RESP` (`0x02`)

```text
offset  field                 type   必須値 / 意味
0       selected_version      u8     0x01
1       device_type           u8     0x01 = AUDIO_SELECTOR
2       firmware_major        u16
4       firmware_minor        u16
6       firmware_patch        u16
8       device_capabilities   u32    機能ビットマップ
12      echoed_host_nonce     u32    HELLO_REQで受信した値
16      boot_id               u32    デバイス起動ごとに変化する値
```

バージョン1では機能ビットを定義しないため、両機能ビットマップは0とする。将来互換の通信で未知の機能ビットを受信した場合は無視する。`boot_id`は起動時に乱数生成することを推奨し、デバイスが再起動するまで同じ値を維持しなければならない。

デバイスは有効な`HELLO_REQ`を受信してから2秒以内に`HELLO_RESP`を送信する。通知されたバージョン範囲内で、自身が対応する最も高いバージョンを選択する。共通バージョンがない場合、可能なら自身が対応するフレームのバージョンで`ERROR(UNSUPPORTED_VERSION)`を送信し、接続を切断する。バージョン1実装が通知する範囲は`[1, 1]`だけとする。

ホストは返送された乱数値、デバイス種別、選択バージョンを検証する。検証失敗時は接続を終了する。有効な応答を受信したホストは2秒以内に完全同期を開始しなければならない。

## 6. エンドポイント識別と同期世代番号

ホストは完全なWindowsエンドポイントIDを内部に保持し、有効な各エンドポイントへ、現在の接続で有効な0以外の`u16`ハンドルを割り当てる。ハンドルは永続的な識別子ではない。

ホストは最初の同期に非0の`u32 generation`を選び、その後の同期ごとに1ずつ増加させる。`0xFFFFFFFF`の次は`0x00000001`とし、0は有効な世代番号として使用しない。

同一通信路接続中、ホストは同じWindowsエンドポイントIDとデータフローに同じハンドルを維持しなければならない。エンドポイントが消失した後、そのハンドルを別のエンドポイントへ再割り当てしてはならない。同じエンドポイントが同一接続中に再出現した場合は以前のハンドルを再利用する。新しい接続ではハンドルの名前空間を作り直し、異なるハンドルを割り当ててよい。このセッション単位の規則により、WindowsエンドポイントIDをバイト列上へ送らずに候補を一覧再構築後も保持できる。

ハンドルを含むすべての要求には世代番号も含める。ホストは現在確定済みの世代番号と一致しない要求を拒否しなければならない。これにより、遅延した要求が一覧再構築後の別エンドポイントを選択することを防止する。

## 7. 完全同期

完全同期を開始できるのはホストだけとする。デバイスは`SYNC_REQ`で開始を要求できる。メッセージ順序を次のとおり固定する。

```text
SYNC_BEGIN
OUTPUT_ENDPOINT を output_count 回
INPUT_ENDPOINT  を input_count 回
CURRENT_OUTPUT  を必ず1回
CURRENT_INPUT   を必ず1回
SYNC_END        を必ず1回
```

1回の同期に属するすべてのメッセージは同じ世代番号を持つ。エンドポイントの送信順は表示および候補巡回順として扱い、基礎となるエンドポイント集合と表示名が変わらない限り安定させなければならない。ホストは表示名の大文字・小文字を区別しない文字コード順の比較で並べ替えし、同名の場合は完全なエンドポイントIDを安定した同順位時の比較値として使用することを推奨する。

デバイスは`SYNC_BEGIN`後に準備中の状態を構築し、部分的な状態を画面へ表示してはならない。有効な`SYNC_END`を受信した時点で、一覧と現在の状態を一括で置換し、11節に従って候補を選択する。

件数不一致、データフロー内のハンドル重複、ハンドル0、非0かつ一覧に存在しない現在値ハンドル、世代番号不一致、不正な順序、または`SYNC_END`前の2回目の`SYNC_BEGIN`を検出した場合、準備中の状態全体を無効とする。デバイスは対応する`ERROR`を送信し、続けて`SYNC_REQ(PROTOCOL_RECOVERY)`を送信する。

出力ハンドルと入力ハンドルは、メッセージ種別によりデータフローを識別できるため同じ数値でもよい。同一データフロー内のハンドルは一意でなければならない。

### 7.1 `SYNC_REQ` (`0x10`)

```text
offset  field    type  値
0       reason   u8    SyncReason
```

| 値 | 同期理由 | 意味 |
| ---: | --- | --- |
| `0x00` | `USER_RECONNECT` | ローカルの再接続または設定画面操作 |
| `0x01` | `STATE_MISSING` | 確定済み状態が存在しない |
| `0x02` | `PROTOCOL_RECOVERY` | 不正または未完了の同期を破棄した |

ホストは500 ms以内に完全同期を開始することを推奨する。複数の未処理要求を1回の同期へ統合してよい。

### 7.2 `SYNC_BEGIN` (`0x11`)

```text
offset  field          type
0       generation     u32
4       output_count   u16
6       input_count    u16
```

各件数は64以下でなければならない。

### 7.3 `OUTPUT_ENDPOINT` (`0x12`) / `INPUT_ENDPOINT` (`0x13`)

```text
offset  field          type
0       generation     u32
4       handle         u16
6       name_length    u16
8       friendly_name  name_length バイトのUTF-8
```

ペイロード長は`8 + name_length`と完全に一致しなければならない。`name_length`は1以上240以下とする。表示名は表示専用であり、エンドポイントの識別に使用してはならない。

### 7.4 `CURRENT_OUTPUT` (`0x14`) / `CURRENT_INPUT` (`0x15`)

```text
offset  field                   type
0       generation              u32
4       console_handle          u16
6       multimedia_handle       u16
8       communications_handle   u16
```

各フィールドはWindowsのロールである`eConsole`、`eMultimedia`、`eCommunications`を表す。そのロールに有効な既定エンドポイントがない場合、またはその既定エンドポイントが送信済みの有効エンドポイント一覧に存在しない場合はハンドル0とする。

バージョン1の画面では`multimedia_handle`を表示上の基準となる現在値とする。これが0なら、`eConsole`、`eCommunications`の順で最初の非0のハンドルを使用する。非0のロール別ハンドルがすべて同一でない場合、デバイスはロール分離状態を視覚表示することを推奨する。デバイスからの設定要求では、分離状態にかかわらずホストが3ロールすべてを要求エンドポイントへ設定する。

### 7.5 `SYNC_END` (`0x16`)

```text
offset  field        type
0       generation   u32
```

## 8. 既定エンドポイント設定

デバイスは確定済み状態に存在するハンドルだけを設定要求に使用する。完全同期適用中に設定要求を送信してはならず、同時に未完了となる設定要求は最大1件とする。

ホストは完全同期送信と設定処理を直列化する。設定要求の受信から`SET_RESULT`送信までの間に無関係な完全同期を開始してはならない。その間のWindows Core Audioの通知は、結果後に必須となる完全同期へ統合する。すでに開始した完全同期と設定要求が競合した場合、ホストは`BUSY`を返してその同期を完了し、その後に結果後の完全同期を送信してよい。

`request_id`はデバイスが選択する非0の`u32`とし、要求ごとに1ずつ増加する。`0xFFFFFFFF`の次は1とする。これによりデバイスは遅延または重複した結果を拒否できる。

### 8.1 `SET_OUTPUT_REQ` (`0x20`) / `SET_INPUT_REQ` (`0x21`)

```text
offset  field        type
0       request_id   u32
4       generation   u32
8       handle       u16
```

ホストは受信時に世代番号を検証し、ハンドルから完全なWindowsエンドポイントIDを解決する。その後、`e`eConsole``、`e`eMultimedia``、`e`eCommunications``の順でエンドポイントを3ロールすべてへ設定する。途中で失敗した場合も含め、応答前に実際の既定状態を再取得する。

### 8.2 `SET_RESULT` (`0x22`)

```text
offset  field              type
0       request_id         u32
4       operation          u8    0x00 出力, 0x01 入力
5       status             u8    `SetStatus`
6       error_code         u16   エラーCodeまたは0x0000
8       known_generation   u32   ホストの確定済み世代番号
```

| 値 | `SetStatus` | 意味 |
| ---: | --- | --- |
| `0x00` | `SUCCESS` | 3ロールすべてが要求どおりであることを検証済み |
| `0x01` | `FAILED` | Windows操作または検証に失敗 |
| `0x02` | `STALE_GENERATION` | 要求世代番号が現在値ではない |
| `0x03` | `INVALID_HANDLE` | 指定データフローにハンドルが存在しない |
| `0x04` | `BUSY` | 状態再構築中で処理できない |

`SUCCESS`の場合、`error_code`は`NONE`とする。それ以外の場合は失敗理由を示すエラーコードとする。結果は処理完了を通知するだけであり、デバイスの現在値を直接変更しない。

成功・失敗を問わず、すべての`SET_RESULT`後にホストは新しい世代番号で完全同期を送信しなければならない。デバイスは任意で成功または失敗を一時表示し、完全同期を確定した時点でのみ実状態を採用する。

設定要求がタイムアウトした場合、デバイスは以前の現在値を維持し、保留中表示を解除して通信エラーを表示し、`SYNC_REQ(STATE_MISSING)`を送信する。

## 9. 生存確認

### 9.1 `PING` (`0x30`) / `PONG` (`0x31`)

```text
offset  field   type
0       token   u32
```

どちらの通信相手も`PING`を送信できる。受信側は2秒以内に同じトークンを持つ`PONG`を返さなければならない。いずれのフレームも10秒間受信していない通信相手はPINGを送信することを推奨する。有効な任意のフレーム受信は受信方向の生存を示すが、保留中のPINGを完了するのは対応するPONGだけとする。

PINGが2回連続でタイムアウトした場合、その通信相手はアプリケーション接続が切断されたものと判断し、通信路を切断してセッションハンドルと未完の同期状態を破棄し、再接続処理へ移行する。各通信相手が同時に保留中にできるPINGは1件だけとする。

## 10. エラー

### 10.1 `ERROR` (`0x7F`)

```text
offset  field                  type
0       error_code             u16   エラーCode
2       related_message_type   u8    不明な場合は0
3       reserved               u8    0
4       context_id             u32   request_id、generation、または0
8       detail_length          u16
10      detail                 detail_length バイトのUTF-8
```

ペイロード長は`10 + detail_length`と完全に一致し、`detail_length`は240以下とする。詳細文字列は診断専用であり、動作判断のために解析してはならない。エラーの応酬を防止するため、`ERROR`に対して別の`ERROR`を返してはならない。有効な設定要求の失敗には`ERROR`ではなく`SET_RESULT`を使用する。

| 値 | エラーコード | 推奨動作 |
| ---: | --- | --- |
| `0x0000` | `NONE` | エラーなし。`SET_RESULT(SUCCESS)`だけで有効 |
| `0x0001` | `UNSUPPORTED_VERSION` | 切断する |
| `0x0002` | `UNKNOWN_TYPE` | 消費済みフレームを無視して継続する |
| `0x0003` | `INVALID_LENGTH` | フレームを破棄し、継続または同期要求 |
| `0x0004` | `INVALID_PAYLOAD` | フレームを破棄し、継続または同期要求 |
| `0x0005` | `INVALID_UTF8` | フレームを破棄し、継続または同期要求 |
| `0x0006` | `UNEXPECTED_MESSAGE` | フレームを破棄し、必要なら状態復旧 |
| `0x0007` | `SYNC_SEQUENCE` | 準備中の状態を破棄し、新しい同期を要求 |
| `0x0008` | `COUNT_MISMATCH` | 準備中の状態を破棄し、新しい同期を要求 |
| `0x0009` | `DUPLICATE_HANDLE` | 準備中の状態を破棄し、新しい同期を要求 |
| `0x000A` | `STALE_GENERATION` | 新しい同期を送信または待機 |
| `0x000B` | `INVALID_HANDLE` | 新しい同期を送信または待機 |
| `0x000C` | `AUDIO_API_FAILURE` | 実状態を再取得して新しい同期を送信 |
| `0x000D` | `AUDIO_VERIFY_FAILURE` | 実状態を再取得して新しい同期を送信 |
| `0x000E` | `BUSY` | 新しい同期後にだけ再試行 |
| `0x000F` | `RECEIVE_BUFFER_OVERFLOW` | 再接続する |
| `0x0010` | `INTERNAL_ERROR` | 復旧できなければ再接続する |

不正フレームからメッセージ種別または関連情報を信頼できる形で取得できない場合、`ERROR`の対応フィールドを0とする。

## 11. デバイスの候補動作

出力と入力はそれぞれ独立した現在値と候補を持つ。

完全同期を確定する際、以前の候補と同じハンドルが新しい一覧にも存在する場合は候補を維持する。6節により同一接続中のハンドル再割り当ては禁止されているため、この比較は安全である。表示名を識別に使用してはならない。

候補を維持できない場合は基準となる現在値を候補とする。現在値が不在の場合は表示順の最初のエンドポイントを候補とする。一覧が空の場合は現在値と候補の両方を不在とする。

LEFTとRIGHTは候補だけを変更し、一覧両端で循環する。CENTERは候補が存在し、未完了要求がない場合だけ設定要求を送信する。現在値はホストからの完全同期を確定した時点でのみ変更する。

ハンドルが安定していても古い世代番号が有効になるわけではない。デバイスはその後のすべての設定要求に、新しく確定した世代番号を使用しなければならない。

## 12. タイムアウトと復旧

| 条件 | タイムアウト / 動作 |
| --- | --- |
| ホストによる最初の`HELLO_REQ`送信 | 通信路接続から2秒以内 |
| デバイスによる`HELLO_RESP`返信 | 有効な要求から2秒以内 |
| ホストによる初回完全同期の開始 | 有効な応答から2秒以内 |
| ホストによる要求済み完全同期開始 | 500 ms以内を推奨 |
| 進行中の完全同期 | `SYNC_BEGIN`から`SYNC_END`まで5秒 |
| 設定処理 | 要求から`SET_RESULT`まで5秒 |
| PONG | PINGから2秒 |
| PING前の無通信時間 | 10秒を推奨 |
| エンドポイント変更デバウンス | 最後の通知から250 msを推奨 |
| 再接続の待機時間 | 1、2、4、8秒、その後最大10秒。ハンドシェイク成功で初期化 |

デバイス側で同期タイマーがタイムアウトした場合、準備中の状態を破棄して`SYNC_REQ(PROTOCOL_RECOVERY)`を送信する。ホスト側で設定処理が5秒を超えた場合、可能なら`SET_RESULT(FAILED, AUDIO_API_FAILURE)`を返し、実状態を再取得して完全同期を実施する。

ホストは、短時間に連続するWindows Core Audioのエンドポイントおよび既定値の変更通知をデバウンス時間で統合し、有効なエンドポイントを再列挙して全ロールの既定値を取得し、1回の完全同期を送信することを推奨する。新しい完全同期は待ち行列内の古い状態を置換できるが、複数の完全同期を互いに混在してはならない。

## 13. 状態遷移

### 13.1 ホスト

```text
DISCONNECTED
  -> SPP_CONNECTED
  -> WAIT_HELLO_RESP       （HELLO_REQ送信）
  -> SYNCHRONIZING         （完全同期送信）
  -> READY
  -> SYNCHRONIZING         （Audio変更、SYNC_REQ、またはSET_RESULT）
  -> READY
```

ホストは無関係な物理または仮想COMポートを探索してはならない。通信先の検出では任意のシリアルポートを開かず、WindowsのBluetooth識別情報およびサービス情報から、ペアリング済みの`AudioSelector` SPPサービスを選択しなければならない。

### 13.2 デバイス

```text
DISCONNECTED
  -> WAIT_HELLO_REQ
  -> WAIT_INITIAL_SYNC     （HELLO_RESP送信）
  -> APPLYING_SYNC
  -> READY
  -> SET_PENDING           （SET_*_REQ送信）
  -> APPLYING_SYNC         （SET_RESULT受信後、完全同期を待機）
  -> READY
```

通信路切断時、両通信相手はパーサーの未完データ、未完了要求、準備中の同期状態、世代番号、ハンドルを破棄する。デバイスは以前表示していた名前を古い情報として画面に残してもよいが、`PC DISCONNECTED`を表示し、新しいハンドシェイクと完全同期が完了するまで設定要求を許可してはならない。

## 15. バージョン管理規則

フレームヘッダーのバージョンはバイト列仕様全体を識別する。バージョン1の受信側が安全に無視できないメッセージまたはフィールドを追加する場合、新しいプロトコルバージョンが必要となる。新しい列挙値または機能ビットを追加できるのは、無視した場合の動作が明確に安全であるか、事前に合意される場合だけとする。

バージョン1では次を固定する。

- ヘッダーおよびペイロード構造を変更しない。
- 予約フィールドは0のままとする。
- 未知のメッセージ種別は消費してエラー通知し、意味を推測しない。
- 不正なメッセージを別のメッセージとして暗黙に解釈しない。
